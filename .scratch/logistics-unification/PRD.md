# Logistics unification: rate-ranked LogisticsRequests over live objects

See [ADR 0008](../../docs/adr/0008-logistics-unification-overmind-style.md) for the full, source-verified design rationale (Overmind and creep-tasks were cloned and read in full — every claim below traces to a specific decision recorded there). This PRD turns that ADR into buildable scope.

## Problem Statement

The colony's transport creeps never carry minerals. Energy is (almost) never simultaneously absent from every provider at once, so the greedy allocator always finds an energy job to do — a starved mineral consumer sits at a fixed, low, static priority tier that can never outrank a routine, always-available energy pickup, no matter how long the mineral has gone unmoved. This is invisible today because minerals are the only non-energy resource in play, but it will only get worse: labs, the factory, and the power spawn are all coming, and each will need a variety of resources moved to and from it competing for the same pool of creeps. The static-priority-tier design cannot scale to that future — it needs a mechanism where genuine urgency (a large, long-starved request) can outrank routine availability (a small, always-there one), for any resource type, not just energy.

## Solution

Replace `src/logistics/graph.ts`'s provider/consumer graph and `allocate.ts`'s tier-first greedy matcher with a rate-ranked request model, adapted from Overmind's `LogisticsNetwork`: every pickup or delivery need becomes one signed `LogisticsRequest` (positive amount = wants resource, negative = has resource to give), and idle creeps greedily pick the request with the best `multiplier × amount / distance` rate — including detours through storage/terminal when that beats a direct trip. Because the rate is computed fresh from live amounts and distances rather than a fixed tier number, a mineral request's score naturally grows until it can outrank a routine energy hop, without any hand-tuned tier reordering. The existing Supply/Transport role split is kept (Supply stays the cheap, energy-only, short-hop fast path for spawn/extension/tower — no rate math needed there, mirroring Overmind's own Queen/Transport split), and Steward gains its own parallel rate-ranked pool for the anchor-link/storage/terminal triangle it already manages by hand-tuned thresholds today.

## User Stories

1. As the colony's transport fleet, I want to rank every pending resource need (energy or otherwise) by a common urgency score, so that a long-starved mineral pickup can win a creep's next trip over a routine energy hop.
2. As a mineral container next to an extractor, I want my accumulated mineral to become a transport request the instant I hold any, so that mineral never waits behind an arbitrary fullness threshold the way energy intentionally does.
3. As an energy container next to a source, I want my output to only become a request once meaningfully full, so that transport creeps aren't sent on trivial trips for a few units of energy.
4. As a transport creep with free capacity, I want to evaluate whether swinging by storage or the terminal first improves my effective delivery rate, so that a multi-leg route beats a suboptimal direct one when the numbers say so.
5. As a transport creep, I want to commit to my picked request until it's fulfilled or invalidated, so that I don't thrash between competing requests every tick and waste CPU re-ranking a decision I already made.
6. As a transport creep whose task becomes invalid mid-route (target drained by someone else, target destroyed), I want to re-rank fresh on my next idle tick, so that I never retry a dead reference forever.
7. As a spawn or extension, I want my energy refill need served by the cheap Supply fast-path, not by Transport's rate-ranked pool, so that routine spawn upkeep isn't competing with (or crowding out) longer-range and multi-resource transport decisions.
8. As a tower, I want my refill need served by Supply the same way a spawn's is, so that an empty tower during an attack is never stuck behind Transport's rate evaluation.
9. As the anchor link, storage, and terminal triangle, I want my own rate-ranked pool (mirroring Transport's, run by Steward), so that link-drain, controller-link top-up, and storage-to-terminal rebalancing compete fairly with each other under the same scoring instead of hand-tuned fixed thresholds.
10. As the source-to-anchor-link and anchor-to-controller-link legs, I want to keep firing as an unconditional, instant, no-travel pass outside any request pool, so that link transfers aren't slowed down or complicated by a rate-ranking system built for creep trips.
11. As a remote container's energy, I want to register as an ordinary withdraw request with no room-boundary special case, so that a remote pickup is judged purely on the same rate math as a local one.
12. As a spawn or extension already being fed by a transporter en route from a remote room, I want my remaining need to shrink in every other transporter's ranking pass as that delivery approaches, so that a second transporter doesn't also get sent to "help" a need that's already covered, while still remaining available if the incoming delivery turns out not to be enough.
13. As a developer, I want request-producing code (miner, mineral miner, hatchery, upgrade site) to each own their own registration logic against live `Game.*` state, so that a structure's transport need is expressed next to the code that understands that structure, not enumerated centrally by a function that has to know about every structure type in the colony.
14. As a developer, I want a creep's in-progress route to persist across ticks in its memory, re-planned only when it goes idle, so that CPU isn't spent re-ranking every transporter's options every single tick.
15. As a developer, I want a creep's committed route to reference its target only by ID in memory (resolved back to a live object when acted on), so that Memory's serialization boundary is respected without threading an ID/live-object indirection through the registration and ranking code that doesn't need it.
16. As a developer reading the codebase later, I want the vocabulary "LogisticsRequest" reserved for this transport-demand concept and never confused with the existing spawn-scheduling "Request" (a missing creep to spawn), so that the two concepts stay unambiguous in code and conversation.
17. As a developer, I want the old `graph.ts`/`allocate.ts`/`logisticsRunner.ts` system to keep running the live bot unmodified while the new system is built and proven correct in parallel, so that the colony is never mid-migration in production.
18. As a developer, I want a single cutover point that swaps Transport (and later Steward) onto the new system and deletes the old files in one commit, so that there's never a state where both systems are partially wired together.
19. As a developer, I want the new system's `Task`/`fork`/`parent` chaining shape written natively in this codebase rather than as a dependency on the (7-years-unmaintained) `creep-tasks` npm package, so that the pattern's design is reused without inheriting a stale external dependency.
20. As a future developer adding lab, factory, or power spawn logistics, I want those structures to register `LogisticsRequest`s the same way energy and mineral do today, so that adding a new resource type to the pool requires no changes to the ranking or matching algorithm itself.

## Implementation Decisions

- **Request model**: One `LogisticsRequest` type replaces `graph.ts`'s separate `Provider`/`Consumer` interfaces. Shape (fields, not literal TS syntax): target (a live game object reference), resource type, signed amount (positive = wants delivered, negative = has to give), a rate (`dAmountdt`, how fast the amount is changing — e.g. a miner's known harvest rate), and a multiplier (urgency scaling factor, defaults to 1). `requestInput`-equivalent and `requestOutput`-equivalent are two constructor functions building this same shape into the same pool, differing only in that the output constructor negates amount/rate before insertion.
- **Ranking**: A request's score for a given idle creep is `multiplier × amount / distance` (Overmind's `dQ/dt` shape), evaluated across multiple candidate routes — direct-to-target, or via a buffer detour (storage, terminal) first — taking whichever route yields the best rate. This replaces `graph.ts`'s static `PRIORITY` tier constants entirely.
- **Matching**: Greedy, single-sided. Each idle creep independently picks its own best-scoring request (mirrors Overmind's actual shipped `handleSmolTransporter`/`transporterPreferences`, not its unused Gale-Shapley stable-matching code). No two-sided stable matching is built.
- **Pool topology**: Two separate rate-ranked pools, not one. Transport's pool covers everything except spawn/extension/tower (energy, minerals, and future lab/factory/powerSpawn resource needs). Supply keeps its own cheap, energy-only, tier-free fast path for spawn/extension/tower exclusively (no rate math — matches Overmind's `TransportRequestGroup`/Queen split, which also doesn't bother with rate math for the same local-refill case). Steward gets a third, structurally identical rate-ranked pool (same request shape, same scoring function) scoped to the anchor link/storage/terminal triangle it already owns. `links.ts`'s two hardwired, unconditional, instant link-firing legs (source→anchor, anchor→controller) are untouched — no creep trip exists there for a rate to apply to.
- **No double counting across pools**: each of the three (Supply, Transport, Steward) only ever sees the subset of live structures/piles it's scoped to; a request never appears in more than one pool.
- **Registration shape**: Self-registration, not a centralized snapshot scan. Each structure/site's own code (miner registering its source container's output, mineral miner registering its container's output, hatchery registering spawn/tower/battery input, upgrade site registering its battery input) builds and inserts its own `LogisticsRequest`(s) against live `Game.*` state at plan time — no `ColonySnapshot` indirection for this subsystem. This is a deliberate, scoped departure from the rest of the planner stack's pure-function-over-snapshot convention; it applies to `src/logistics/` only, not a signal to migrate mining/building/spawning off snapshots.
- **Registration threshold asymmetry**: Energy container output registers as a request only once meaningfully full (a threshold, not "any amount"), with `dAmountdt` set from the source's known saturation/harvest rate. Mineral container output registers unconditionally, the instant it holds any amount, with no threshold and no `dAmountdt` — mineral accrues slowly in cooldown-gated bursts, so a fullness gate would reproduce, in miniature, the exact starvation this whole rewrite exists to fix.
- **Remote/cross-room pickups**: No special-casing, no room-boundary guard on the withdraw side, no `travelHome`-style "don't reserve a deliver leg" safeguard. A remote container's energy registers as an ordinary request, priced by the same rate math (which naturally discounts it for distance). The spawn/extension reservation-span concern this replaces is instead handled by a predicted-amount discount: every other creep already routed toward a given request has its incoming/outgoing resource amount subtracted from that request's remaining amount on every fresh ranking pass, so a spawn already being fed by a remote-bound transporter continuously becomes less attractive to rank toward — a soft, self-correcting discount, not a hard reservation lock. This requires a `targetedBy`-equivalent: a ref-keyed map of "which live creeps are currently routed toward this target," derived fresh at the start of each planning pass by scanning every live Transport/Steward creep's persisted current task (same pattern as today's `allocate.ts` `ReservedAmounts` folding) — not a write-time cache requiring explicit invalidation.
- **Fan-out**: One request maps to one trip (at most 2 legs: an optional buffer detour, then the target), matching Overmind's shape exactly. Today's multi-stop behavior (one loaded creep topping off several nearby same-tier extensions in one trip) is deliberately dropped, not ported forward as a codebase-specific extension. The old behavior remains recoverable from git history for a later A/B comparison once the new shape is running live.
- **Task persistence and chaining**: A creep's committed route persists in its memory across ticks and is only re-ranked when the creep goes idle (no task, or the current task's target/validity check fails) — never re-ranked every tick for every creep. The chain/route representation itself adopts the `Task`/`fork()`/`parent` shape from `bencbartlett/creep-tasks` (same author as Overmind, published as its own standalone, multi-consumer package, though unmaintained since 2019): `fork(newTask)` makes `newTask` the new current task with the prior task demoted to `parent`; completion walks back to the parent. This is written natively in this codebase — no dependency is taken on the actual `creep-tasks` npm package, since it's 7 years unmaintained with no compatibility guarantee against current TypeScript/`@types/screeps`.
- **Memory-boundary indirection**: The live-object reference (`LogisticsRequest.target`) is used directly during same-tick registration and ranking — no tag/resolve union needed there. The one place an ID-based indirection remains structurally necessary is the *persisted* task in creep memory (Memory is serialized and cannot hold a live object reference): it stores a bare ID, resolved back to a live object only when the creep acts on its current task tick.
- **Vocabulary**: The new signed-request concept is named `LogisticsRequest`, not the bare word "Request" — the codebase's `CONTEXT.md` already defines "Request" for the unrelated spawn-scheduling concept (a missing creep to spawn). Both entries in `CONTEXT.md` cross-reference each other; always qualify as "spawn Request" or "LogisticsRequest" where the bare word is ambiguous. `Provider` and `Consumer` (the interfaces being replaced) move to `CONTEXT.md`'s `_Avoid_` list under `LogisticsRequest`.
- **Migration sequencing**: Build the new system end-to-end in parallel with the old (a new module, not edits to `graph.ts`/`allocate.ts` in place), proven correct against the mockup-server integration seam before any live wiring changes. The existing live bot keeps running unmodified on the old system throughout. One cutover commit swaps Transport onto the new system, deletes `graph.ts`/`allocate.ts`, and rewrites `logisticsRunner.ts` against the new task shape. Steward's migration to its own new pool may land in the same cutover or a following one — sequencing between Transport's and Steward's cutover is an implementation-time call, not fixed by this PRD.
- **Scope boundary**: This PRD covers `src/logistics/` and the Transport/Steward-consuming parts of `src/behaviors/` only. It is explicitly not a decision to migrate `src/mining/`, `src/colony/` building, or spawn planning off the `ColonySnapshot` pattern.

## Testing Decisions

- **One seam: the mockup-server integration harness.** Per the live-object registration decision above, this subsystem's registration and ranking logic reads `Game.*` directly — there is no pure-function boundary left to unit-test with hand-built fixtures the way `test/unit/logistics/graph.test.ts` and `allocate.test.ts` (1131 lines total, to be deleted at cutover, not adapted) do today. All new tests drive the real bundled bot through `test/integration/harness.ts`'s `BootedColony` (boots a real `screeps-server-mockup` private server, one tick at a time) and assert on observed world state — energy/mineral reaching the right sinks, request priority ordering producing the right creep behavior — never on intermediate data structures internal to the ranking pass.
- **Prior art**: `test/integration/drop-mining.test.ts` and `test/integration/remote-mining.test.ts` are the closest existing precedent — both boot a colony, drive it forward tick-by-tick with a `CheckpointLadder`, and assert on `roomObjects()`/`structures()`/`hasRole()` rather than internal state. New tests for this feature follow the same shape: seed or wait for the relevant structures (an extractor + mineral container, a lab/factory placeholder if applicable, a remote source), then assert the resource in question actually moves to the expected sink within a tick budget.
- **What "good" looks like here**: tests assert observable behavior only (a mineral pile shrinks and storage's mineral store grows; a starved mineral request eventually outranks a routine energy hop and gets served within some tick budget; a spawn under-fed for N ticks by remote-return traffic still gets topped up by a second transporter once the first's predicted delivery proves insufficient) — never on the internal rate score of a specific request or the shape of a specific `LogisticsRequest` object, since those are implementation details of the ranking pass, not contracts the rest of the codebase depends on.
- **Regression watch**: the dropped multi-stop fan-out behavior (one creep topping off several extensions per trip) is a known, deliberate behavior change — Supply already owns spawn/extension refill day to day, so this isn't expected to regress the integration suite's existing checkpoints, but if `boot-rcl2.test.ts`/`rcl3.test.ts`-style benchmarks show slower spawn-fill timing after cutover, that's the first place to look.

## Out of Scope

- Two-sided stable matching (Gale-Shapley) — Overmind's own shipped code doesn't use it either; not building it here.
- Any lab, factory, or power spawn structure/role implementation — none exist in this codebase yet. This PRD makes the request/ranking model ready for them, but does not add their structures, roles, or registration call sites.
- Market trading (`createOrder`/`deal`) — unrelated, already tracked separately, untouched by this PRD.
- Migrating `src/mining/`, `src/colony/` building, or spawn planning off the `ColonySnapshot` pure-function pattern.
- Restoring multi-stop fan-out (one creep, many same-tier consumers per trip) as a codebase-specific extension on top of the ported model — deliberately deferred; may be revisited later via an A/B against the pre-cutover git history.
- Taking the `creep-tasks` npm package as a dependency.
- Any change to `links.ts`'s existing hardwired link-firing legs.
