# Logistics unification: rate-ranked requests over live objects, Overmind-style

Status: accepted (design). Supersedes nothing. Covers the full architecture, algorithm, request/task shapes, and dependency policy for the `logistic-overhaul` branch's logistics rewrite, reached via a source-verified design grill against the actual Overmind and creep-tasks repositories (cloned and grepped in full, not read from docs or summaries). `src/logistics/graph.ts`, `allocate.ts`, `src/behaviors/logisticsRunner.ts`, and their tests are expected to be rewritten, not incrementally patched. Implementation itself (exact interface field lists, function signatures, migration PRs) is out of scope for this ADR and is expected to happen test-first, informed by everything decided here — see the sequencing decision below.

## Context

`graph.ts`'s `providers()`/`consumers()` rank consumers by a **static priority tier** (tower=90 > controllerContainer=80 > storage=70 > spawnSystem=60 > builder=40 > upgrader=30). Because energy providers are almost never simultaneously empty, `allocate.ts`'s greedy nearest-fill matcher always finds an energy job to do. A starved mineral consumer sits at a fixed low tier with no way to ever outrank a routine, always-available energy pickup — no matter how long it's gone unserved. This was fine while energy was the only resource in play; it breaks as soon as minerals (and later labs/factory/powerSpawn) need to compete for the same transport creeps.

Investigated Overmind (bencbartlett/Overmind) directly from source — a full clone, not docs — to see how a mature bot solves this. Two corrections to initial (docs-derived) assumptions surfaced during that reading, both confirmed by grepping the full cloned repo, not a single file:

- Overmind is not one unified pool. It's a locality/actor split: `TransportRequestGroup` (flat priority-tiered, no rate math) serves the bunker-core `Queen`, which only ever touches structures in its fixed quadrant; `LogisticsNetwork` (rate-based) serves the roving `Transport` role. Plain spawn/extension/tower refills go through the cheap tiered pool; only the hatchery's *battery* (a dedicated buffer) and mineral output go through the rate-based one.
- Overmind's live `TransportOverlord.run()` calls `handleSmolTransporter` (greedy single-sided "pick my best-rated request") unconditionally for every transporter. `handleBigTransporter`/`stableMatching()` (real Gale-Shapley) is fully implemented and even partially wired (a lazy `matching` getter, a `carryThreshold: 800 // RCL4+` config value gating "big" transporters) but has zero callers anywhere in the repo. It reads as an abandoned mid-migration, not a considered "greedy is better" decision — but abandoned or not, greedy-with-a-good-rate-metric is what Overmind actually ships and runs.

## Decision

**Keep the Supply/Transport locality split; generalize both.** Mirrors Overmind's Queen/Transport split. Supply remains the short-hop, energy-only, cheap fast path for spawn/extension/tower (no rate math needed — Overmind's own tiered pool doesn't bother with it either). Transport becomes the one pool where energy, minerals, and future lab/factory/powerSpawn requests compete fairly by urgency. Rejected: collapsing to one single pool — would lose the reason Supply exists today (transport queuing on spawn tiles ahead of storage/controller work, already fixed once per `graph.ts`'s own comments) and re-solving that problem some other way wasn't worth it just to avoid a locality split Overmind itself also has.

**Replace static priority tiers with a rate metric** (`multiplier × amount / distance`, Overmind's `dQ/dt` shape) for Transport's request ranking. This is the actual fix for the root problem: a starved/large mineral request's score can now grow to outrank a routine energy hop, instead of being structurally capped below it forever.

**Keep greedy assignment; swap only the ranking function.** Matches Overmind's real shipped behavior (see Context) rather than its unfinished stable-matching code. `allocate.ts`'s existing per-creep "find my best option" loop stays structurally; only what it optimizes changes.

**Port buffer-detour evaluation now, not deferred.** A request's rate score accounts for multiple routes (direct-to-target vs. via storage/terminal first), same as Overmind's `bufferChoices()`. This replaces `allocate.ts`'s current chain-building (`buildPickupChain`/`buildDeliverChain`, `MAX_CHAIN_HOP`) rather than sitting alongside it — storage/terminal detours become routing options scored as part of picking a request, not a separate post-selection pass.

**Adopt Overmind's 1-request-1-trip shape, not today's multi-stop fan-out.** Today, one loaded creep can fan out across many same-tier consumers in a single trip (e.g. topping off 4 nearby extensions). Overmind's rate model has no equivalent — each consumer is matched independently, at most a 2-leg route (buffer → target). Explicitly chosen to drop fan-out for now rather than bolt it on as a codebase-specific extension: the old multi-stop behavior remains recoverable from git history for an A/B comparison once Overmind's shape is running, rather than committing to preserve it sight-unseen.

**Self-registration reads live `Game.*` objects directly, not `ColonySnapshot`.** Request-producing code (mining site registers its own container/mineral output, hatchery registers its own spawn/tower/battery input, upgrade site registers its own battery input) matches Overmind exactly: live references read at plan time, no snapshot indirection. This is a deliberate, scoped departure from the rest of the planner stack, which is pure-function-over-`ColonySnapshot` by repo-wide convention (see `graph.ts`'s own top-of-file comment, and every other planner boundary). Rejected: keeping registration snapshot-driven as smaller distributed pure functions (still testable with fixtures) — considered as a middle path, explicitly turned down. Pure-unit-test capability for this subsystem is accepted as a real cost, traded for tests that exercise real mechanics against the actual mockup server (`test/integration/`, which already boots a real `screeps-server-mockup` colony — this isn't a new test tier, just a shift in which tier logistics tests primarily live in) instead of hand-built fixtures.

Scope: this live-object, self-registration shape applies to `src/logistics/` only for this rewrite. It is not (yet) a decision to migrate `src/mining/`, `src/colony/` building, or spawn planning off the `ColonySnapshot` pattern — if those follow later, that is separate future work, not bundled into this branch.

**Keep persisted per-creep task memory; re-plan only when idle.** Verified against the cloned repo (not assumed): Overmind's `Zerg.task` setter writes `memory.task = task.proto`, rehydrated via `initializeTask()` on the getter — genuinely persisted, multi-tick. `Overlord.autoRun` (`Overlord.ts:505-519`) only invokes the rate-ranking task handler when `creep.isIdle` (no task, or `task.isValid()` false); every other tick it just calls `creep.run()` against the already-persisted task, no re-ranking. This matches — and now doubly justifies — this codebase's existing model (`memory.logistics.current`, re-planned only when idle) and its own CPU-hotpath finding (`logisticsRunner.ts`'s 2026-08-13 profiling note on `runTransport`). Rejected: re-ranking every transporter every tick — an earlier read of Overmind's architecture wrongly assumed this was its mechanism; corrected after checking `Zerg.ts`/`Overlord.ts` directly.

**Collapse `Provider`/`Consumer` into one signed `Request` type.** Checked precisely: Overmind has exactly one type, `LogisticsRequest{id, target, amount, dAmountdt, resourceType, multiplier}`, and exactly one array (`this.requests`). `requestInput()`/`requestOutput()` are two constructor functions building the *same* shape into the *same* array — `requestOutput` just flips `amount`/`dAmountdt` negative before pushing. Provider and Consumer do not exist as separate types anywhere in Overmind's model; the sign of `amount` is the only thing that was ever "provider vs. consumer." `graph.ts`'s current `Provider`/`Consumer` interfaces are replaced by one `Request` type (signed `amount`: positive = wants resource delivered, negative = has resource to pull), matching this exactly — `allocate.ts`'s separate provider-list/consumer-list handling collapses into ranking one array by rate, mirroring `transporterPreferences()`. See [CONTEXT.md](../../CONTEXT.md)'s **Request** (logistics) entry for the vocabulary distinction from the existing spawn-scheduling **Request**/**Requester** terms.

**Steward gets its own rate-ranked pool, same shape as Transport's; `links.ts` stays untouched.** Checked Overmind directly: `LinkNetwork` is a genuinely separate class (own `receive`/`transmit` queues, its own "greedy matching algorithm" per its own file header) — not folded into `LogisticsNetwork`. And `LogisticsNetwork.buffers` (what `bufferChoices()` detours through) is hardcoded to `[storage, terminal]` only; links never appear in it. This corrects an earlier (wrong) claim made mid-grill that links were "part of the buffer network" — they're an unrelated mechanism that happens to also move energy. Given that correction, the decision: Steward's link/storage/terminal rebalancing becomes real request objects (amount, `dAmountdt`, `multiplier`) scored by the *same* rate function Transport uses, matched greedily within Steward's own separate pool — mirrors Overmind's Queen (own `TransportRequestGroup`-consuming pool) vs. Transport (own `LogisticsNetwork`-consuming pool) split exactly, just with both pools now sharing one rate-scoring implementation instead of Overmind's two different ones (tiered vs. rate-based). `links.ts`'s instant, no-creep, zero-travel legs remain a third, genuinely separate mechanism — there is no creep trip to rank, so a rate metric has nothing to apply to.

**Drop `travelHome`'s hard reservation-span guard; adopt Overmind's predicted-amount discount instead.** Today's `allocate.ts` gives a loaded creep found outside its home room a bare `travelHome` task (no chained deliver) specifically so a spawn/extension consumer is never reserved for a whole ~40-60 tick remote round trip (see `types.ts`'s `LogisticsTask.next` doc). Checked whether Overmind's rate-ranked model has an equivalent gap: `requestInput` (deliver-side registration) rejects any out-of-room target outright, but `requestOutput` (withdraw-side) has no such guard — a remote container's energy is an ordinary request, and a transporter can be matched to a remote pickup paired with a home deliver leg immediately, same tick. This looked at first like a real gap (a spawn slot pinned for the whole trip) until `predictedRequestAmount` (`LogisticsNetwork.ts:403-447`) was read in full: `target.targetedBy` is a list, not a lock, and every other transporter already targeting that same request has its carried/incoming resource **subtracted** from the request's predicted remaining amount (`predictedAmount = max(predictedAmount - resourceInflux, 0)`) every time *any* transporter re-evaluates it. A spawn already being fed by a remote-bound transporter mathematically shrinks toward "not worth another trip" for every other transporter's ranking pass, continuously — a soft, self-correcting discount, not a hard reservation. This is a better mechanism than `travelHome`'s binary "don't reserve at all" rule: it lets a second transporter still legitimately help if the first one's incoming amount doesn't cover the full need, something `travelHome`'s all-or-nothing gate can't express. The rewrite adopts this discount mechanism and drops `travelHome` as a distinct concept — this was reached only after two rounds of the assistant asserting an incorrect claim about Overmind's model (first "it's just distance, no safeguard," then "it's a hard reservation for the whole trip") and being pushed to verify against the actual code both times; recorded here so a future reader trusts the mechanism, not the process that found it.

**The `targetedBy`-equivalent is derived fresh each tick, not a write-time cache.** Checked Overmind's actual mechanism: `targetedBy` is a getter on `RoomObject.prototype` reading a single global `Overmind.cache.targets[ref]` map, written exactly once — the `Zerg.task` setter appends the assignee's name when a task with a target is assigned — and requiring an explicit `invalidateCache()` call (seen in `TransportOverlord.handleTransporter`) to stay correct as multiple transporters get matched within the same tick. Rather than porting that write-time/invalidate-on-write shape, the rewrite derives the equivalent the same way `allocate.ts`'s existing `ReservedAmounts` already does: scan every live Transport/Steward creep's persisted current task fresh at the start of each planning pass and build a ref-keyed map from that. No new class of cache-invalidation bug is introduced; the predicted-amount discount (above) is computed from this derived map instead of `ReservedAmounts`' hard subtraction.

**Mirror Overmind's energy-vs-mineral registration asymmetry exactly.** Checked the real registration call sites: `Miner.registerEnergyRequests` (`miner.ts:182-192`) only registers its container's output once it's above a threshold (80% of transport capacity post-bootstrap, 50% during bootstrap) — not the instant it holds anything — and sets `dAmountdt` to the miner's own known harvest rate (`this.energyPerTick`), so a fast source's container looks more urgent sooner. `Extractor` (mineral mining, `extractor.ts:60`) registers with **no threshold at all** — any mineral in the container immediately becomes a request, no `dAmountdt`. This is deliberate, not an oversight: energy accrues continuously and a trivial container amount isn't worth a trip (mirrors this codebase's own `DROP_WORTHWHILE_FLOOR` reasoning in `graph.ts`), while mineral accrues slowly in cooldown-gated bursts — gating it behind a fullness threshold would reproduce, in miniature, the exact starvation pattern this whole rewrite exists to fix. `Miner`'s and `MineralMiner`'s own registration functions in the rewrite follow this same asymmetry: energy container output is threshold-gated with `dAmountdt` set from the source's known saturation rate; mineral container output registers unconditionally the instant it holds anything, no threshold, no `dAmountdt`.

**`NodeRef`'s tag/resolve indirection survives only at the memory-persistence boundary, not in registration/ranking.** `NodeRef` (`types.ts`) exists today as a tagged union (`{kind:"structure",id}`, `{kind:"dropped",id}`, `{kind:"spawnSystem"}`, …) solely because it had to be plain data inside a `ColonySnapshot` and get resolved back to a live object by `logisticsRunner.ts`'s `resolveNode()`. Overmind's `LogisticsRequest.target` is a live object directly (`LogisticsTarget = EnergyStructure | StoreStructure | StructureLab | StructureNuker | StructurePowerSpawn | Tombstone | Resource`) — no tag, no resolve step — because registration already reads `Game.*` (see the live-object registration decision above). The rewrite follows suit for same-tick registration/ranking: `LogisticsRequest.target` holds the live object directly, and `resolveNode()`'s multi-kind resolution logic goes away from that layer. The one place indirection is still structurally required is **creep memory**: `Memory` is serialized and can't hold a live object reference, so the *persisted* task (the cross-tick `current` task, per the task-persistence decision above) still stores a bare id, resolved back to a live object only when the creep acts on it — the same deref-on-read shape as Overmind's own `Task.proto` → `Task.target` getter. This is not a design choice so much as a hard requirement of `Memory`'s serialization; it is now correctly scoped to only the persistence boundary, rather than threaded through the whole registration/ranking pipeline the way today's `NodeRef` is.

**Adopt `creep-tasks`' `Task`/`fork()`/`parent` shape in place of `LogisticsTask.next`.** Checked the origin precisely: Overmind's `Task` (`fork(newTask)` makes `newTask` the creep's new current task with the original demoted to `parent`; "Task is changed to parent upon completion" per `Task.ts:41`) is published as its own standalone package, [bencbartlett/creep-tasks](https://github.com/bencbartlett/creep-tasks) — same author as Overmind, not an independent-origin community standard the way e.g. Traveler (a different author, adopted across many unrelated bots) is, but genuinely factored out as a reusable, multi-consumer library rather than kept Overmind-internal. Functionally this is identical to today's `LogisticsTask.next` (advance-on-completion chain, arbitrary depth via the same recursive-getter shape) — just linked in the opposite direction (`parent` = what runs after, vs. `next` = what runs after). Given the buffer-detour decision above caps a real trip at 2 legs (buffer, then target), the rewrite adopts `creep-tasks`' `Task`/`fork`/`parent` naming and shape directly rather than keeping `LogisticsTask`'s own naming for an equivalent mechanism — chosen for alignment with a genuinely reusable, externally-validated pattern, not because the current shape was deficient.

**Reimplement the `Task`/`fork`/`parent` shape natively; do not take the `creep-tasks` npm dependency.** Cloned `bencbartlett/creep-tasks` to check its real state: published, versioned (`v1.3.0`, typed, `dist/index.js` entry point), but last committed 2019-02-04 — unmaintained for years, same vintage as the Overmind repo itself. An external dependency that stale is a real liability (no security patches, no compatibility guarantee against current TypeScript/`@types/screeps`), and everything *around* this shape (registration, ranking, remote handling, the `targetedBy`-equivalent) is already being reimplemented in this codebase's own idiom rather than consumed from Overmind directly — taking the actual package for just this one piece would be inconsistent with that and would still require its own integration work to interoperate with this codebase's memory shape, logging, and error handling. The `Task` class (or equivalent) is written natively in `src/logistics/` (or `src/behaviors/`), matching only the *shape* (fork/parent/completion-walks-to-parent) recorded above.

**Build the new pool alongside the old; cut over once green.** Given the size of this rewrite (new request/task shapes, live-object registration, a second Steward pool, a new `targetedBy`-equivalent), the new system is implemented end-to-end and proven correct against the mockup server before touching or deleting `graph.ts`/`allocate.ts`/`logisticsRunner.ts` — the live bot keeps running on the old system the whole time. One deliberate cutover commit swaps Transport (and Steward, once its pool is ready) onto the new system and deletes the old files. Rejected: incremental in-place rewriting (swap the ranking function first, then registration, then task shape, keeping tests green at each step) — smaller diffs, but leaves the live system running on a partially-migrated model with old and new assumptions coexisting in the same files for the duration, harder to reason about correctness mid-rewrite than a clean parallel build.

## Consequences

- `graph.ts` and `allocate.ts` as pure functions over `ColonySnapshot` are both being replaced, not extended — expect most of `src/logistics/`'s existing tests to be rewritten against live/mockup fixtures rather than adapted.
- The rest of the planner stack (mining, building, spawning) is now visibly inconsistent with logistics on the snapshot-vs-live question. Future readers should not assume this ADR licenses the same move elsewhere without its own justification.
- Losing multi-stop fan-out is a real, deliberate regression risk for extension-refill throughput specifically — mitigated by Supply already owning that workload day to day (Transport's fan-out loss mostly doesn't bite the common case), and by the old implementation staying available in git history for a direct comparison if it turns out to matter.
- Buffer-detour evaluation (multiple scored routes per request) is more upfront complexity than a direct-distance-only rate metric would have been — accepted now to avoid a second redesign once storage-detour behavior is needed for real (which the mineral/lab/factory use cases make likely).
- The predicted-amount discount replaces `ReservedAmounts`' hard per-tick folded reservation (`allocate.ts`'s `providerRemaining`/`consumerRemaining` maps) with a continuous soft discount computed from live `targetedBy` lists. This needs its own `Game.*`-level equivalent of `targetedBy` (Overmind's `Zerg`/`Task` layer tracks it natively; this codebase has no such registry yet) — a real, non-trivial piece of new plumbing, not a drop-in swap.
